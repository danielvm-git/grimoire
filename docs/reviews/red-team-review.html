Does Grimoire check that my repos follow my patterns?

Three reviewers looked at all 12 checks, the specs, the user docs and the template repo from three angles: coverage, correctness and architecture. This page merges what they found with a read of every doc in the project.

Verdict
Partially

Grimoire is good at running scripts across the fleet and showing the results. But it checks repos against its own hardcoded rules, not against your template. Those rules already disagree with the template in several places, and a few rules can never fail. Today, a green repo in Grimoire does not mean the repo follows your patterns.

Why a green repo can still be off-pattern

Reviewer findings merged by the kind of damage they do. Ordered from most to least harmful to your trust in the dashboard.

1 · false green

Failures that never show up

  • Most pattern checks are severity: warning (has-readme, license-exists, ci-cd-migration, lint-passes). Spec 04 and spec 06 say warnings never change repo health, so an off-pattern repo still looks OK.
  • ci-cd-pipeline-audit exits 0 when only medium rules fail. Permissions, concurrency, file naming and caching are printed but recorded as a pass.
  • 7a/7b are hardcoded to pass (#52). 9a stops scanning after the first scoped workflow (#50).
  • no-secrets, lint-passes, uv-lock-fresh and ci-green exit 0 when their tool is missing or gh isn't logged in. Missing tooling looks like a pass.
2 · wrong rulebook

Grimoire and the template disagree

  • The template's own "recommended" thin ci-cd.yml fails ci-cd-migration.
  • SHA pinning: the template requires a 40-character SHA, but Grimoire accepts @v4 (#55).
  • The template also disagrees with itself. portfolio-standards.md and migration-check.py treat ci-cd-*.yml as current, while start-new-project and Grimoire treat it as legacy.
  • Rules only the template checks, with no Grimoire check: timeout-minutes, ubuntu-latest, agent symlinks.
3 · blind spots

Repos that are never looked at

  • Config supports only a static repo: list or a GitHub team:, and you're a personal account. So 66 repos are listed by hand.
  • Checked today: 4 active repos are missing (big-gowrite, big-quiqui-v2, big-remote-control, bigpowers-factory). 13 listed repos return 404 and 5 are forks.
  • New repos are never audited until you remember to add them.
4 · one size fits all

No stack profiles

  • The template has 12 per-stack pipelines (Python, Go, Godot, static, Swift, MkDocs…), but Grimoire has no stack field. A Godot game and a Python CLI get the same lint → test → build → release → deploy checklist (see #59).
  • Each check guesses the stack by looking for files like pyproject.toml.
5 · no "how far behind"

A boolean can't show compliance

  • CheckResult is one passed flag plus text. The audit's 30+ sub-rules live only in an ASCII table inside output.
  • No per-rule results, no compliance score, no template version per repo, no repo × pattern matrix, no trend.
6 · upkeep

Rules are hard to change safely

  • The pipeline audit is 35 KB of Python inside a YAML block scalar. Nothing lints or type-checks it, and nothing tests its behaviour. The only test checks that the file loads.
  • Every template change means a hand edit in another repo, and nothing tells you when the two drift apart.

critical · verified

On the Docker image, most tool checks skip and pass

Scripts without a shebang run under /bin/sh, which is dash on the python:3.13-slim image. Dash reads if ! command -v X &>/dev/null as "run in the background", so the "not installed, skipping" branch always runs, and that exits 0. This affects ci-green, no-secrets, no-todo-fixme, lint-passes, composer-lock-fresh, uv-lock-fresh and charmcraft-fetch-lib. The image also doesn't install gitleaks, rg, shellcheck, composer, php or charmcraft. Fix: use >/dev/null 2>&1 or a bash shebang, install the tools, and report a missing tool as a failure.

security

A real-looking key in the template repo, and command injection in a check

  • no-secrets found a Context7 API key committed in danielvm-git/.github (specs/plans/WIRE_GLOBAL_MCPS.md). Rotate it. The check's output didn't say where the hit was.
  • lint-passes.yaml:59 pastes PHP file names straight into sh -c, so a file named x$(cmd).php runs that command with GH_TOKEN in its environment.
audit internals

New bugs in ci-cd-pipeline-audit

  • The "primary" pipeline is picked alphabetically, so it lands on ci.yml instead of test-build-release.yml.
  • Only the first deploy file is checked, and deploy-*.yml sorts before deploy.yml.
  • Matching words against str(dict) breaks in both directions. 9c and 9b can never fire. 5c, 6a and 4b always pass ("check" matches inside actions/checkout, "version" inside node-version). Comments are enough to satisfy 5h.
  • 5f reports task-definition or disk- as a critical leaked secret, because they contain "sk-".
  • A build-and-test job fails 3c as critical, because it's checked for a dependency on itself.
  • 8a flags local ./ actions and never scans job-level reusable uses: …@main.
  • 2a fails every workflow_call or schedule workflow. That accounts for 21 of the template's own failures.

Recommended path

Make the template the single rulebook, and make Grimoire the runner and viewer. Each step is useful on its own.

  1. Stop the false greens (days)Replace &>/dev/null in every check (or add a bash shebang), and install the missing tools in the image. Make pattern checks severity: error or add a third "non-compliant" health state. Make "tool missing" a failure instead of a pass. Have the audit exit non-zero on medium findings, or split those into their own check. Fix #50 and #52.
  2. Track the fleet automaticallyAdd an owner: source (all non-archived, non-fork repos of a user or org) with exclude. Remove the 13 dead and 5 forked entries from config.yaml.
  3. Add the top missing checks by reusing template scriptsAgent symlinks, the workflow baseline (timeout-minutes, concurrency, no ubuntu-latest), real branch protection through gh api, Conventional Commits on the default branch, and strict SHA pinning.
  4. Move the rules into the template, pinned by SHAPut a conformance package in danielvm-git/.github: one function per rule, each with an id, a severity and applies_to stacks, plus golden fixtures. Grimoire config gets template: {repo, ref}, and a single check runs it with --json. First fix the template's own ci-cd-* contradictions.
  5. Stack profiles and a compliance matrixAdd stack: per repo (auto-detected, with an override), a RuleResult table, and a page with repos as rows and rules as columns. Show a compliance % and how many template versions each repo is behind.
